# SLB 物理层参数登记册（Param Registry）

> 面向 AI 分模块实现物理层协议时的**跨模块参数真源（SSOT）**。  
> 当前阶段：已落地 **L0+L1 登记册** + **`SlbPhySessionConfig` 字段表** 初稿。  
> 协作流程已封装为 Skill：`slb-param-registry`（先粗提 / 后对齐修改）。

---

## 1. 背景

当前工作：

1. 按协议节号整理**技术文档**（边界、参数、步骤、约束）；
2. 再由 AI **分模块**把技术文档转化成代码实现；
3. 模块之间需要参数互通，部分模块还要消费**上层下发**的配置。

已有能力：

- 分册技术文档内规定的参数表、上下游边界；
- `nearlink-naming`（命名与单位后缀）；
- `slb-doc-generator`（文档骨架与约束写法）；
- 6.6「接口暴露」范本（对外类型与 API 边界）。

缺口在于：**参数定义仍散落在各分册 `.tex` 中**，没有一份跨模块共用的登记真源。各模块独立 vibecode 时，容易出现：

- 同名异义 / 异名同义；
- 私自复制 magic number（如 120000、161）；
- 不清楚谁写、谁读、能否改；
- 上层字段在 PHY 内被「猜写」或二次解析 ASN.1。

因此需要先建立 **L0 + L1 参数登记册**，作为后续 Skill、接口暴露文档与代码生成的共同地基。

---

## 2. 为什么要做（原因）

| 原因 | 说明 |
|------|------|
| **跨模块互通** | 加扰、调制、功控、映射、定位编排都要读同一套基准与会话配置 |
| **AI 实现约束（harness）** | 仅靠口头提示无法保证一致性；登记册是可引用、可校验的硬约束入口 |
| **文档会迭代** | 各人分册会改；登记册用 `status`（frozen/draft）吸收变更，不必等齐终稿 |
| **所有权清晰** | 每条参数标明归属节号与读写方，避免「每个模块各写一套」 |
| **为 SessionConfig 铺路** | L1 字段表直接对应未来的 `SlbPhySessionConfig` |

一句话：**先固定「全 PHY 共用 + 上层下发」的量，再谈模块专有参数与运行时交换量。**

---

## 3. 参数如何划分（四层模型）

| 层 | 名称 | 生命周期 | 谁写 | 谁读 | 本阶段 |
|----|------|----------|------|------|--------|
| **L0** | 系统常量 | 基本不变 | 标准/工程约定（只读表） | 全 PHY | **本册已覆盖，合作者进行合并** |
| **L1** | 会话/上层配置 | 按接入/重配更新 | 上层软件开发平台 | 各 PHY 库只读 | **仿真开发者提供，并与字段表对齐** |
| **L2** | 模块专有可调参数 | 随本模块配置 | 本模块 owner | 本模块 + 边界导出 | 后续按库补 |
| **L3** | 运行时交换量 | 事件/测量/命令时交换 | 生产者模块 | 消费者模块 | 后续随接口暴露补，合作者之间协调 |

### 读写约定

- **L0**：禁止在业务模块内再定义同义常量；一律引用登记册 `id` / 生成头文件。
- **L1**：仅上层写入；PHY 子模块**禁止**自行改 MCS、`P_o`、角色表等；只读消费。
- **L2/L3**：后续展开完整表；在登记册中仅保留「后续安排」说明。

### 状态约定（适应文档迭代）

| status | 含义 |
|--------|------|
| `frozen` | 数值/语义已可作当前工程真源（仍以正式标准为准） |
| `draft` | 已从现有分册抽出，但依赖他章/他人文档或字段名可能对齐调整 |
| `tbd` | 已知需要，但本工作区文档不足，待对齐后补 |



---

## 4. 合作者目前该做的任务



| 该做 | 不该做 |
|------|--------|
| 用 `slb-param-registry` Skill，只提**自己分册相关**的 L1/L2/L3 | 每人另写一份互不相干的「全局参数表」 |
| 先 Phase A 粗提（`draft`/`tbd`），再 Phase B 对齐升 `frozen` | 等齐所有人终稿才动手 |
| 合并进本目录共享登记册 / SessionConfig | 在模块代码里私建 120000、161 等常量 |

1：汇总各位组员负责的相关技术文档中，所需要的L0,L1参数。并在后续组内进行评审，完成全局参数方面的对齐

2：L1参数为 SessionConfig 字段表，为只读方式，其来自上层接入物理层，根据项目背景，需要合并所有合作者的L1字段表，与上层仿真平台调用端进行对齐。



## 6. 后续安排（建议顺序）

1. **组内评审** L0/L1 登记册 + SessionConfig 字段表（同名同义）。  
2. **各模块负责人**按 Skill Phase A 补各自边界参数。  
3. **vibecode 约束**：生成代码时强制 `nearlink-naming` + `slb-param-registry`（只引用登记册/Session）。  
4. **按模块补 L2 + 接口暴露**（先发送主链，再测量/定位）。  
5. **补 L3**；可选导出 `registry.yaml` / 生成 `slb_phy_session.h`。

---

## 7. 使用方式（给 AI / 实现者）

```
Use slb-param-registry skill. airMode=slb (nearlink-naming).
```

1. 先整体提取登记册 / SessionConfig；  
2. 在组内讨论对齐后，L0/L1 **只引用、不改写**；  
3. 新跨模块量：先 Phase A 登记（`draft`），再改文档/代码；  
4. 对齐后 Phase B 升 `frozen`。
